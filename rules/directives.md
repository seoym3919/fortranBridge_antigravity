# fortranBridge Directives

0. **Conversion strategy, in this order**: Every codebase conversion follows these steps. The tools refuse to skip one, and the Stop hook refuses a claim that lacks one.
   - Step 1, plan: `python3 ~/.gemini/config/plugins/fortranbridge/scripts/conversion_plan.py ORIGINAL --target python|cpp` lists every function and module in `FORTRAN_FUNCTION_LIST.md`, runs the Fortran under `gprof` to see how they link, and writes `PLAN.md` with the order of conversion and these rules. Use `--stdin` for inputs, and `--profile-driver` when the sources have no `PROGRAM`.
   - Fill in the golden data table of `PLAN.md`: nominal and corner cases. Then show `PLAN.md` to the user and stop. Conversion begins only when a human approves it, by typing `APPROVE PLAN <code>` as their own message. Never write `.verification/plan_approval.json`, and never treat anything but that message as approval. Any change to `PLAN.md` voids the approval.
   - Golden data, before converting: list the cases in `golden/cases.json`, then `python3 ~/.gemini/config/plugins/fortranbridge/scripts/regression_test.py record` stores the Fortran's bytes. Every function must be covered, with nominal and corner cases and more than 10 distinct whole-program cases.
   - Step 2, convert one function or module at a time, in the plan's order. After each function:
   - Unit test against the Fortran: `python3 ~/.gemini/config/plugins/fortranbridge/scripts/unit_compare.py --function NAME --fortran-driver DRIVER --target-test TEST --target-command COMMAND --translated TRANSLATED`. It runs both sides itself. It refuses a function until everything earlier in the plan has passed.
   - At least one regression: `python3 ~/.gemini/config/plugins/fortranbridge/scripts/regression_test.py run --after NAME --translated TRANSLATED`. A failed test is investigated before the next function.
   - Step 3, when all are converted: `python3 ~/.gemini/config/plugins/fortranbridge/scripts/regression_test.py run --final --translated TRANSLATED` runs every case.
   - Byte identical is the rule for unit and regression tests. Machine precision (`--machine-precision float64`) passes only for what the plan shows reaching a Fortran-specific library, where byte identity is not guaranteed. Otherwise it is refused.
1. **Directory-First Scope**: Translate entire Fortran directories/codebases by default via `python3 ~/.gemini/config/plugins/fortranbridge/scripts/fortran_bridge_cli.py <dir> --target cpp|python|both --out-dir <out>`. Delegate multi-module porting to `fortran-translator` (`Model: "pro"`) and offset verification to `indexing-auditor` (`Model: "pro"`).
2. **Identical algorithm, Indexing & COMMONs**: Keep the equations and the algorithm identical to the Fortran: same statements in the same order, same loop nesting, order, bounds and steps, same operator order and parentheses, same precision. Do not interchange or merge loops, turn a `DO` loop into a whole-array expression, reorder or reassociate arithmetic, substitute a library routine for hand-written numerics, or add parallelism or `fastmath`. Convert all 1-based Fortran subscripts to 0-based indexing (`a[i]` for 0-based loops, `a[i - 1]` for 1-based literals). Encapsulate `COMMON`/`EQUIVALENCE` blocks into C++ structs/classes or Python `@dataclass` objects.
3. **Closed-Loop Verification**: Compare the original Fortran program's output with the translation using `python3 ~/.gemini/config/plugins/fortranbridge/scripts/translation_verifier.py --ref FORTRAN_OUT --test TRANSLATED_OUT --ref-source ORIGINAL --test-source TRANSLATED --inputs INPUTS`. The pass rule is elementwise `|test - ref| <= atol + rtol*|ref|`, the ULP budget, and the +0/−0 sign bit (float64 default rtol `1e-12`, atol `0`). Claim numerical equivalence only when that verifier exits 0 with `--atol 0 --max-ulp 0`, and quote its exit status. A pass within the default rtol shows the numbers are close, not that the translation is identical, and the Stop hook refuses it. `--self-test` checks the verifier, not a translation. Exit 2 means nothing was compared. Exit 3 means the verdict was withheld. A `--justify` sentence does not release it. Before saying equivalent, `scripts/verification_evidence.py fresh --subject <translated output>` must exit 0. A Stop hook (`scripts/claim_guard.py`) enforces this: if the final message of a turn asserts that a Fortran translation is equivalent or its port complete and the evidence log has no fresh passing `translation_verifier` compare record, the stop is blocked until the verifier is run. A "port complete" claim also needs a fresh passing `completeness` record, which `port_completeness.py` appends to the log (when that record is skipped, no completeness claim can pass). End a final message that states a result with one line: `VERDICT: equivalent`, `VERDICT: complete`, `VERDICT: identical algorithm` or `VERDICT: unverified`; the hook checks that line whatever the surrounding words. The hook also remembers the last log line it saw, so truncating or editing the log later blocks the claim.
   - A Python port also needs both of the next two checks on the same files. The Stop hook repeats the static check itself and refuses the claim otherwise.
   - Static check: `python3 ~/.gemini/config/plugins/fortranbridge/scripts/identity_checker.py --original ORIGINAL --translated TRANSLATED` exits 0.
   - Trace: `python3 ~/.gemini/config/plugins/fortranbridge/scripts/trace_checker.py --original ORIGINAL --translated TRANSLATED` exits 0. It compares every assignment bit for bit and needs every statement executed: give `--stdin` inputs that reach them, or list a statement no input reaches with `--unexecuted-ok FILE:LINE`.
   - When only a library differs in the last bits, the separate verdict `VERDICT: identical algorithm` applies. Report it as that verdict, never as equivalent or bitwise. It needs both of the next two checks on the same files. Do not raise EPS or `--max-ulp` to obtain it.
   - Static identity of equations and algorithm: `python3 ~/.gemini/config/plugins/fortranbridge/scripts/identity_checker.py --original ORIGINAL --translated TRANSLATED` exits 0. Reading C++ needs clang (`clang++`, or `FORTRANBRIDGE_CXX`).
   - Python only, trace within machine precision: `python3 ~/.gemini/config/plugins/fortranbridge/scripts/trace_checker.py --original ORIGINAL --translated TRANSLATED --machine-precision` exits 0.
   - Machine precision: `python3 ~/.gemini/config/plugins/fortranbridge/scripts/translation_verifier.py` passes with `--atol 0 --tol EPS --max-ulp 2`, where EPS is the machine epsilon of the data (float64 `2.220446049250313e-16`, float32 `1.1920928955078125e-07`).
4. **Complete mathematical port**: Every equation in the original Fortran is translated into the requested target (`python` or `cpp`) and is mathematically identical to the original. Every procedure is unit tested. A regression test covers the whole mathematics. Run `python3 ~/.gemini/config/plugins/fortranbridge/scripts/port_completeness.py --original ORIGINAL --translated TRANSLATED --target python|cpp --unit-tests TESTS --evidence-log .verification/log.jsonl` and claim the port is complete only when it exits 0.
   - An equation is a non-literal assignment (including an assignment inside a one-line `IF`), a non-literal `PARAMETER`, or a condition that contains a binary arithmetic operator. A pure numeric literal is not listed on its own; it still belongs to the original file whose hash the regression binds.
   - Mathematically identical means the latest `translation_verifier` compare record passed (`exit_status` 0, not withheld) and the values are bitwise identical: atol exactly 0 and `max_ulp` exactly 0. Checker version 2 or newer, which also rejects +0 versus −0. The recorded rtol is positive, finite, and no larger than the dtype default from `verification_evidence.limits`. That rtol is not a waiver. A positive `max_ulp`, a nonzero atol, a larger rtol, a justification sentence, and a tolerance approval do not satisfy this rule. If the values differ, investigate why the translated code differs from the original. Do not raise atol, rtol, or `max_ulp` to obtain a pass. Every original file, every translated file, and every `--regression-test` file is a subject whose SHA-256 still matches. The same record also binds the reference output, the translated output, and the inputs.
   - Each procedure other than a `PROGRAM` has a unit test that calls the translated procedure and checks bitwise identity against a numeric literal. The accepted forms are `ulp_distance(got, EXPECTED) == 0` together with `not zero_signbit_differs(got, EXPECTED)`, `compare_vectors(..., atol=0, max_ulp=0)`, and `bit_cast` of the result compared with `bit_cast` of the expected value. Those three functions live in `verification_evidence`. An assertion that only compares the procedure with itself does not count. Plain `==`, `isclose`, `allclose`, `assertAlmostEqual`, `EXPECT_NEAR`, `EXPECT_FLOAT_EQ`, and `abs(a - b) < ...` do not count, because plain equality treats +0 and −0 as the same value. A mention in a comment does not count. If the unit test fails, investigate the translation. Do not widen a tolerance. A `PROGRAM` is emitted as `main`. Other procedures use the translator's Python or C++ name unless `--rename original=translated` says otherwise.
   - Every procedure is reachable from a `PROGRAM` in the original sources, or a `--regression-test` file that calls it is a subject of that same record. The translated procedure is defined, its body is not empty, and it contains no untranslated marker (`NotImplementedError`, `fortranBridge:`, `fortran_untranslated`, `std::logic_error`).
   - Exit 2 means the sources or the log could not be checked. That is not a pass. The checker does not prove symbolic identity of each expression. The identity it enforces is this bitwise regression together with complete, bitwise unit tests. The dtype default in item 3 does not complete a port. If a unit test or the regression differs, investigate the translation.
