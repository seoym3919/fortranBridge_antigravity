\begin{abstract}
Decades of foundational scientific simulations in astrophysics, fluid dynamics, climate modeling, and particle physics exist exclusively in legacy Fortran (FORTRAN 66/77 and early Fortran 90). Migrating this critical software into modern computational ecosystems---specifically modern C++ (C++17/20) and vectorized scientific Python (NumPy, SciPy, Numba)---is hindered by profound semantic divergences: 1-based versus 0-based array indexing, column-major versus row-major memory stride order, unthread-safe \texttt{COMMON} block global state, unstructured \texttt{GOTO} control flow, and subtle intrinsic function roundoffs. This manual presents the design, algorithms, and theoretical guarantees of \textbf{fortranBridge}, an automated translation engine designed for Google Antigravity. We formulate formal transformation rules for index normalization, memory contiguity loop transposition, \texttt{COMMON} block encapsulation, formatted I/O decompilation, dataflow intent inference, multi-file topological dependency linking, and closed-loop floating-point round-trip verification certifying numerical equivalence ($\operatorname{Rel } L_2 \le 10^{-12}$).
\end{abstract}

    \item \texttt{/link-project <dir>}: Analyzes multi-file \texttt{MODULE}/\texttt{USE} dependencies and generates \texttt{CMakeLists.txt}.
    \item \texttt{/infer-intents <dir>}: Performs dataflow analysis to infer \texttt{const T\&} in C++ and return tuples in Python.

\section{Introduction and the Fortran Migration Mandate}
% =============================================================================

Fortran has served as the backbone of high-performance scientific computing since its introduction by John Backus in 1957. Production codes built over seven decades contain millions of lines of rigorously verified numerical algorithms. However, modern scientific software infrastructure demands features absent in legacy Fortran:
\begin{enumerate}
    \item \textbf{Object-Oriented and Functional Modularity}: Safe state encapsulation, thread safety, and dependency injection.
    \item \textbf{GPU and Heterogeneous Acceleration}: CUDA, SYCL, Kokkos, and JAX/PyTorch tensor primitives.
    \item \textbf{Modern Memory Semantics}: Zero-overhead abstractions like \texttt{std::span}, \texttt{std::vector}, and contiguous NumPy arrays.
    \item \textbf{Interoperability and Ecosystem Integration}: REST APIs, interactive Jupyter environments, and machine learning libraries.
\end{enumerate}

Manual translation of legacy Fortran into C++ or Python is notoriously error-prone. Even experienced computational scientists frequently introduce subtle off-by-one subscript errors, inadvertent cache-thrashing memory strides, and uninitialized aliasing defects. \textbf{fortranBridge} provides an automated, mathematically rigorous translation pipeline designed to solve these systemic issues.

\section{Indexing Paradigms and Off-by-One Guarding}
% =============================================================================

\subsection{1-Based to 0-Based Coordinate Translation}
The most prevalent source of catastrophic translation failure is the disparity between Fortran's default 1-based indexing and C++/Python's 0-based indexing:
\begin{equation}
    \text{Fortran: } A(1), A(2), \dots, A(N) \quad \longleftrightarrow \quad \text{C++/Python: } a[0], a[1], \dots, a[N-1].
\end{equation}

When translating loops of the canonical form:
\begin{lstlisting}[language=Fortran]
      DO 10 I = 1, N
         A(I) = B(I) + C(I)
 10   CONTINUE
\end{lstlisting}
\texttt{fortranBridge} applies unified index coordinate transformation:
\begin{equation}
    i_{\mathrm{C++}} = i_{\mathrm{Fortran}} - 1, \quad i_{\mathrm{C++}} \in [0, N-1].
\end{equation}
In C++, this yields:
\begin{lstlisting}[language=C++]
for (int i = 0; i < n; ++i) {
    a[i] = b[i] + c[i];
}
\end{lstlisting}
And in Python, when loop vectorization is not possible:
\begin{lstlisting}[language=Python]
for i in range(n):
    a[i] = b[i] + c[i]
\end{lstlisting}
Where vectorization is applicable, the entire loop reduces to a single vectorized statement:
\begin{lstlisting}[language=Python]
a = b + c
\end{lstlisting}

\subsection{Arbitrary and Negative Lower Bounds}
Fortran permits arbitrary array dimensions:
\begin{equation}
    \texttt{DIMENSION A(L\_1:U\_1, L\_2:U\_2)}.
\end{equation}
For an array declared as \texttt{DIMENSION A(-5:5, 0:10)}, the index mapping for element $A(i, j)$ into 0-based C++ coordinates is:
\begin{equation}
    i_{\mathrm{C++}} = i - L_1 = i - (-5) = i + 5, \quad j_{\mathrm{C++}} = j - L_2 = j - 0 = j.
\end{equation}
The \texttt{indexing-auditor} agent formally verifies that all shifted array subscripts are non-negative and strictly bounded by the allocated dimension extent $U_k - L_k + 1$.

\section{Memory Layout and Memory Contiguity Transposition}
% =============================================================================

\subsection{Column-Major vs. Row-Major Storage}
Consider a 2D matrix $A \in \mathbb{R}^{M \times N}$. The linear memory offset of element $A(i, j)$ differs fundamentally across programming paradigms:
\begin{align}
    \text{Fortran (Column-Major): } & \operatorname{offset}(i, j) = (i - 1) + (j - 1) \cdot M, \\
    \text{C / C++ (Row-Major): } & \operatorname{offset}(i, j) = i \cdot N + j.
\end{align}

In Fortran, the first index $i$ varies fastest in linear memory. Consequently, canonical Fortran algorithms nest loops with $I$ in the innermost position:
\begin{lstlisting}[language=Fortran]
      DO 20 J = 1, M
         DO 10 I = 1, N
            A(I, J) = B(I, J) * C(I, J)
 10      CONTINUE
 20   CONTINUE
\end{lstlisting}

\begin{proposition}[Cache Line Contiguity Principle]
If a Fortran nested loop is translated naively to C++ without loop or array transposition:
\begin{lstlisting}[language=C++]
// Cache-Destructive Naive Translation (Stride = N doubles per iteration):
for (int j = 0; j < m; ++j) {
    for (int i = 0; i < n; ++i) {
        a[i][j] = b[i][j] * c[i][j]; // Cache miss on every memory fetch!
    }
}
\end{lstlisting}
Memory access jumps across rows by stride $N$, loading a 64-byte cache line but consuming only a single 8-byte double before jumping, destroying L1/L2 data cache hit rates.
\end{proposition}

\texttt{fortranBridge} addresses this by applying \textbf{Loop Stride Inversion}:
\begin{lstlisting}[language=C++]
// Cache-Optimal Transposed C++ Translation:
for (int i = 0; i < n; ++i) {
    for (int j = 0; j < m; ++j) {
        a[i][j] = b[i][j] * c[i][j]; // Sequential, SIMD-vectorizable memory loads
    }
}
\end{lstlisting}
Or, when interfacing with external Fortran-ordered libraries, explicitly retaining column-major ordering via \texttt{Eigen::Matrix<double, Dynamic, Dynamic, ColMajor>} or NumPy's \texttt{order='F'}.

\section{Global State Encapsulation: COMMON and EQUIVALENCE}
% =============================================================================

\subsection{COMMON Block State Encapsulation}
Legacy Fortran codes share variables between subroutines using global memory layouts known as \texttt{COMMON} blocks:
\begin{lstlisting}[language=Fortran]
      SUBROUTINE STEP_ORBIT
      COMMON /ORBIT_DATA/ ECC, SEMI, INC, POS(3), VEL(3)
      ...
      END
\end{lstlisting}

In modern concurrent C++ and multi-threaded Python, global mutable state leads to catastrophic data races and prevents re-entrant simulation instances.

\texttt{fortranBridge} translates each named \texttt{COMMON /NAME/} block into a dedicated state structure:
\begin{lstlisting}[language=C++]
// Modern C++ Encapsulated Struct
struct OrbitDataBlock {
    double ecc{0.0};
    double semi{0.0};
    double inc{0.0};
    std::array<double, 3> pos{};
    std::array<double, 3> vel{};
};

// Subroutine accepts state reference
void step_orbit(OrbitDataBlock& orbit_state);
\end{lstlisting}

In Python, \texttt{fortranBridge} translates the block into a typed \texttt{@dataclass}:
\begin{lstlisting}[language=Python]
from dataclasses import dataclass, field
import numpy as np

@dataclass
class OrbitDataBlock:
    ecc: float = 0.0
    semi: float = 0.0
    inc: float = 0.0
    pos: np.ndarray = field(default_factory=lambda: np.zeros(3))
    vel: np.ndarray = field(default_factory=lambda: np.zeros(3))
\end{lstlisting}

\subsection{EQUIVALENCE Statement De-Aliasing}
In FORTRAN 77, \texttt{EQUIVALENCE} statements force variables to share physical memory locations:
\begin{lstlisting}[language=Fortran]
      DIMENSION VEC(3)
      EQUIVALENCE (VEC(1), X), (VEC(2), Y), (VEC(3), Z)
\end{lstlisting}
The \texttt{equivalence\_analyzer} engine identifies whether the aliasing represents:
\begin{itemize}
    \item \textbf{Scalar-to-Vector Overlay}: Decompiled to C++ references (\texttt{double\& x = vec[0];}) or Python tuple unpacking.
    \item \textbf{1D Flat Buffer to 2D Matrix Reshaping}: Decompiled to zero-copy \texttt{std::span<double>} or NumPy strided memory views (\texttt{mat = flat.view().reshape((M, N), order='F')}).
    \item \textbf{Type Punning}: Decompiled to C++20 \texttt{std::bit\_cast} or explicit unions.
\end{itemize}

\section{Control Flow De-Spaghettification and Formatted I/O}
% =============================================================================

\subsection{Arithmetic IF and Computed GOTO}
\begin{equation}
    \texttt{IF (E) L1, L2, L3} \quad \Longleftrightarrow \quad \begin{cases}
        \text{Jump to } L_1 & \text{if } E < 0, \\
        \text{Jump to } L_2 & \text{if } E = 0, \\
        \text{Jump to } L_3 & \text{if } E > 0.
    \end{cases}
\end{equation}
This is decompiled into standard C++ \texttt{if (e < 0) ... else if (e == 0) ... else ...} blocks. Similarly, \texttt{GOTO (L1, L2, L3) I} is decompiled into a C++ \texttt{switch(i)} or Python \texttt{match/case} construct.

\subsection{Fortran FORMAT to C++20 std::format and Python f-Strings}
Fortran formatted I/O uses cryptic descriptor strings:
\begin{lstlisting}[language=Fortran]
 100  FORMAT(1X, 'ENERGY = ', 1P, E15.7, 2X, 'STEP = ', I6)
      WRITE(6, 100) ENERGY, ISTEP
\end{lstlisting}
The \texttt{format\_decompiler} engine maps descriptors to modern typesafe string formatters:
\begin{align}
    \text{C++20: } & \texttt{std::cout << std::format(" ENERGY = \{:15.7e\}  STEP = \{:6d\}\textbackslash n", energy, istep);} \\
    \text{Python: } & \texttt{print(f" ENERGY = \{energy:15.7e\}  STEP = \{istep:6d\}")}
\end{align}

\section{Static Dataflow Intent Inference}
% =============================================================================

Because FORTRAN 77 lacked argument intent keywords, all arguments were passed as mutable pointers. The \texttt{intent\_analyzer} engine constructs a definition-use (def-use) dataflow graph for each routine:
\begin{itemize}
    \item \textbf{INTENT(IN)}: Variables only read in expressions $\longrightarrow$ \texttt{const T\&} or pass-by-value in C++; standard input parameter in Python.
    \item \textbf{INTENT(OUT)}: Variables only written to $\longrightarrow$ \texttt{T\&} in C++; extracted from caller arguments and returned as clean tuple in Python (\texttt{return out1, out2}).
    \item \textbf{INTENT(INOUT)}: Variables both read and updated $\longrightarrow$ mutable \texttt{T\&} in C++; in-place array modification in Python.
\end{itemize}

\section{Multi-File Project Linking and Topological DAG}
% =============================================================================

Production scientific simulations consist of numerous interdependent files. The \texttt{project\_linker} engine scans codebases, identifying:
\begin{equation}
    \text{Dependency Edges: } \mathcal{E} = \{ (F_i, F_j) \mid F_i \text{ uses MODULE or calls routine defined in } F_j \}.
\end{equation}
It executes a topological sort on the resulting Directed Acyclic Graph (DAG) to determine the strict compilation order and emits modular C++ headers (\texttt{.hpp}) with \texttt{\#pragma once} alongside a turnkey \texttt{CMakeLists.txt}.

\section{Closed-Loop Numerical Equivalence Verification}
% =============================================================================

The \texttt{translation\_verifier} and \texttt{f2py\_harness} modules conduct closed-loop numerical testing comparing legacy Fortran output against translated C++ or Python implementations across parameter phase space:
\begin{align}
    \operatorname{Rel } L_2 &= \frac{\|\mathbf{y}_{\mathrm{Fortran}} - \mathbf{y}_{\mathrm{Port}}\|_2}{\|\mathbf{y}_{\mathrm{Fortran}}\|_2 + \varepsilon} \le 10^{-12}, \\
    \operatorname{Rel } L_\infty &= \frac{\max |\mathbf{y}_{\mathrm{Fortran}} - \mathbf{y}_{\mathrm{Port}}|}{\max |\mathbf{y}_{\mathrm{Fortran}}| + \varepsilon} \le 10^{-12}.
\end{align}

Any discrepancy exceeding machine roundoff ($10^{-15}$) indicates an off-by-one indexing error, inverted coordinate frame, or precision mismatch.
